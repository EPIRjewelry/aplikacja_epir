## Summary — ustalenia (przed implementacją)

Incydent 2026-10-07: cron `0 9 * * *` UTC (`runOperatorReportCron` → `runOperatorDailyReport`) zakończył się `D1_ERROR: Network connection lost.`. Catch-up eksportu w tym samym przebiegu doszedł do końca (`batch_exports.updated_at` 09:00:28 UTC), więc awaria była **po** catch-up, wewnątrz `runOperatorDailyReport`.

### Które wywołanie D1 rzuciło błąd

W `runOperatorDailyReport` łańcuch to:

1. `buildFlowHealthReport` — wiele zapytań D1 (`DB` + `DB_CHATBOT`)
2. `fetchGemmaConversations24h` — `DB_CHATBOT` (messages/sessions)
3. `persistOperatorDailyReport` — `INSERT … ON CONFLICT` na `DB_CHATBOT.operator_daily_reports`
4. opcjonalny webhook HTTP (nie D1)

**Co może przerwać crona (niezłapany throw):**

| Krok | Binding | Zachowanie przy D1 error |
|------|---------|--------------------------|
| `loadExportStatus` / `countPixel24h` / `countMessages24h` | DB / DB_CHATBOT | swallow → metryki `-1` |
| `countPixelNullSessions24h` | `DB` | **rzuca** |
| `computeChatPixelSessionMatch` | `DB_CHATBOT` + `DB` | **rzuca** |
| `fetchGemmaConversations24h` | `DB_CHATBOT` | swallow → pusta sekcja Gemma |
| **`persistOperatorDailyReport`** | `DB_CHATBOT` | **rzuca** — brak wiersza w `operator_daily_reports` |

Bez logu CF z dokładnym stackiem nie da się wskazać jednego statementu 1:1. Przy symptomie „brak wiersza w `operator_daily_reports`” i udanym catch-up na `DB`, najwęższe miejsca to:

1. **`persistOperatorDailyReport`** (zapis SSOT) — najbardziej bezpośrednia przyczyna braku raportu,
2. albo wcześniejszy throw z **`computeChatPixelSessionMatch` / `countPixelNullSessions24h`** (cron pada przed zapisem).

Oba są przejściowe przy `Network connection lost.` i wymagają retry + jawnego fail po wyczerpaniu prób.

### Idempotencja zapisu

**Już jest upsert** po `report_date` (PK):

```sql
INSERT … ON CONFLICT(report_date) DO UPDATE SET
  markdown_body = excluded.markdown_body,
  edog_verdict = excluded.edog_verdict,
  created_at = excluded.created_at
```

Ponowienie / ręczne odtworzenie nie dubluje wiersza.

### Plan implementacji (ten PR)

1. Wspólny helper retry (3 próby, exponential + jitter) tylko dla przejściowych błędów D1 (udokumentowana lista).
2. Retry wokół krytycznych kroków D1 raportu + ustrukturyzowany log `step` przy finalnym fail; cron kończy się błędem jawnie.
3. Odtworzenie za datę: metoda RPC na `BigQueryBatchS2SRpc` (ten sam `runOperatorDailyReport`, opcjonalna `date`) — scope istniejący `bigquery.analytics_query`. **Bez** `EPIR_OPERATOR_PANEL_SECRET`. **Bez nowego sekretu** (auth = S2S service binding + `ctx.props.scopes`).
4. Treść raportu / werdykt EDOG bez zmian. Bez deployu.
